# Privacy Architecture, Data Governance & Compliance Assumptions

## 1. Executive Summary & Privacy Posture
The **Tenant-Aware Storage & Capacity Forecaster** operates under strict data minimization and privacy-by-design principles adhering to the European Union **General Data Protection Regulation (GDPR)** and India's **Digital Personal Data Protection Act (DPDP)**. 

To ensure zero risk of confidential disclosure, intellectual property leakage, or regulatory non-compliance, this reference implementation operates exclusively on **100% synthetic, pseudonymised telemetry**. No production customer databases, raw row payloads, proprietary column values, or Personally Identifiable Information (PII) are ever accessed, stored, or processed by the forecaster.

---

## 2. Core Privacy Guarantees

### 2.1 Complete Synthetic Data Generation
All data residing in `data/saas_capacity.db` is procedurally generated by `scripts/generate_data.py`:
- **Tenant Identifiers**: Formatted as opaque, monotonically indexed strings (`tenant_001` to `tenant_050`).
- **Organizations**: Opaque synthetic domain entities (`org_1` to `org_5`).
- **User Accounts**: Synthetic role test accounts (`usr_plat_admin`, `usr_tenant_org1`, etc.).
- **Schema & Table Names**: Generic relational schema names (`schema_tenant_001`, `users`, `orders`, `events_stream`, `audit_logs`).
- **Zero Real Data**: No production snapshots, customer dumps, or live query logs were utilized in training or benchmarking.

### 2.2 Telemetry-Only Data Minimization
The forecasting system observes strictly metadata and high-level aggregation counters. At no point does the system query or inspect the contents of rows:
- **Observed Metrics**:
  - Daily row count (`rows`)
  - Storage footprint in gigabytes (`table_size_gb`, `index_size_gb`)
  - Daily write mutations (`writes`)
  - Daily read queries (`queries`)
- **Excluded Content**:
  - No customer names, email addresses, phone numbers, or credentials.
  - No transactional payloads, freeform text fields, or document attachments.
  - No SQL query strings, parameter bindings, or customer application logic.

### 2.3 Strict Pseudonymization & Isolation
In a production deployment, tenant database connections would utilize separate connection pools, distinct database users, and schema-level grants. Customer identifiers are hashed or pseudonymized before ingestion into the capacity warehouse.

## 3. Regulatory Alignment Matrix (GDPR / DPDP)

| Regulatory Principle | SaaS Forecaster Implementation & Safeguards |
|:---|:---|
| **Data Minimization (GDPR Art. 5(1)(c))** | The forecaster collects only four numeric scalar metrics per table per day (`rows`, `table_size_gb`, `index_size_gb`, `writes`, `queries`). No individual user records or message payloads are processed. |
| **Purpose Limitation (GDPR Art. 5(1)(b))** | Collected telemetry is strictly bound to infrastructural capacity planning, disk exhaustion forecasting, and quota governance. It is never reused for behavioral profiling or user analytics. |
| **Storage Limitation (GDPR Art. 5(1)(e))** | Capacity telemetry is retained for **13 months (395 days)** to capture annual seasonality and year-over-year baseline growth, after which older records are permanently purged. |
| **Integrity & Confidentiality (GDPR Art. 5(1)(f))** | Role-Based Access Control (RBAC) enforces strict boundary isolation between tenant organizations. External partners only see explicitly delegated tenant schemas. |
| **Accountability & Audit (DPDP Sec. 8)** | All configuration mutations (updating storage limits, modifying retention policies, approving capacity) are recorded in an append-only, immutable `audit_logs` table. |

---

## 4. Retention Policy for Capacity Metrics

To balance historical trend modeling with storage efficiency and compliance standards:

1. **Daily Metrics Horizon**: Retained for exactly **13 months (395 days)**. This allows 30-day and 90-day momentum calculations and year-over-year seasonal adjustments while adhering to storage minimization requirements.
2. **Forecast Snapshot Horizon**: Generated forecast records are retained for **90 days** to support ongoing accuracy auditing and model drift tracking, after which they are rolled up into monthly summary aggregates.
3. **Audit Log Horizon**: Compliance audit logs (`audit_logs`) are retained for **3 years** in immutable storage to fulfill enterprise governance and SOC 2 / ISO 27001 audit requirements.

## 5. Security & Boundary Architecture

```mermaid
graph TD
    subgraph Multi-Tenant Database Layer
        S1[(Tenant 001 Schema)]
        S2[(Tenant 002 Schema)]
        Sn[(Tenant 050 Schema)]
    end

    subgraph Metadata Extraction (Read-Only)
        EX[DB Metadata Collector / Information Schema]

    subgraph Capacity Forecaster Warehouse
        CW[(saas_capacity.db)]
        CW_T[Opaque Metrics: rows, size_gb, writes, queries]
        CW_A[Immutable Audit Logs]
    end

    subgraph RBAC Guarded API Layer
        API[FastAPI Gateway]
    end

    subgraph Consumers
        R1[Platform Admin: Full Heatmap]
        R2[Tenant Admin: Scoped to Org]
        R3[Partner: Delegated Tenants Only]
        R4[Auditor: Backtest & Audit Logs Only]
    end

    S1 -.->|Schema stats only| EX
    S2 -.->|Schema stats only| EX
    Sn -.->|Schema stats only| EX
    EX -->|Pseudonymised aggregates| CW
    CW --> API
    API -->|X-Role: platform_admin| R1
    API -->|X-Role: tenant_admin| R2
    API -->|X-Role: external_partner| R3
    API -->|X-Role: auditor| R4
```

1. **Authentication & Authorization**: Requests to the API gateway require verified role and organization headers (`X-Role`, `X-Org-Id`, `X-User-Id`).
2. **Access Isolation**: Cross-tenant data access is blocked at the database query layer. Tenant administrators cannot retrieve or infer storage utilization of other organizations.
3. **Auditability**: Every administrative action that touches storage limits or retention configurations creates an immutable event in `audit_logs` with actor metadata, timestamp, and modification payload.
